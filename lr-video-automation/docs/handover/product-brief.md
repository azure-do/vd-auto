# 動画投稿自動化：設計とゴール（外部共有用）

- 出典: `docs/baseline/動画投稿自動化_AIオーケストレーション引継ぎ.md`（2026-07-27作成）からの抜粋
- 抜粋方針: 社内の体制・依頼経緯・過去のインシデント記録を除き、**設計とゴールのみ**を残す
- 原本は `docs/baseline/`（変更禁止）。本書は外部共有用の派生物であり、原本と食い違った場合は原本が正
- 対象: ダンススクールLr（現在8支部、今後増加予定）

## 1. 目的

講師がレッスン後の縦動画を1回提出すると、本部確認を経て以下へ配信される仕組みを作る。

```text
講師が動画を1回提出
  ↓
講師・支部・クラスを自動判定
  ↓
元動画を保管
  ↓
SNS用動画を生成
  ↓
本部へLINE承認通知
  ↓
承認後に媒体別処理
  ├─ YouTube：元動画を支部別チャンネルへ投稿
  ├─ Instagram：加工版を該当支部アカウントへ投稿
  └─ TikTok：加工版を1アカウントへ投稿または投稿準備
```

最初の目的は「確実にアップロード・投稿できること」。高度なAI編集は、投稿経路が安定した後に追加する。

### 前提方針

- 講師の操作は増やさない。既存の講師ポータルから動画を選択して提出するだけにする。
- 既存本番システムは、新システムの検証が終わるまで変更・停止しない。
- 元動画はそのまま支部別YouTubeへ投稿する。
- Instagram用は加工し、該当支部のInstagramへ投稿する。
- 投稿前の本部確認を残し、LINEで承認する。
- 外部ライブラリ `VideoUploaderLib` への依存を廃止し、ソース・認証・運用を自社管理にする。
- 秘密情報をチャット・Git・コード・ログへ出さない。

## 2. 講師側のUX

講師は現在、GitHub Pages上の講師ポータルをリンク集・掲示板として使っている。

- リポジトリ: `syoshinsya-dance-school-web/lr-portal`
- 公開方式: GitHub Pages
- 主なファイル: `index.html`、`portal-data.json`
- 現在「【提出】レッスン後の動画送信」からGoogleフォームを開いている。

新システムでは、Googleフォームへのリンクをポータル内のアップロード画面へ置き換える。

通常時の講師操作:

```text
「レッスン後の動画送信」をタップ
↓
動画を選択
↓
「提出する」をタップ
```

講師には原則として次を入力させない。

- 支部 / 講師名 / スタジオ / ジャンル / タイトル / ハッシュタグ / 投稿先

本人確認は、現在Googleフォームで取得しているGoogleメールアドレスを利用する。講師マスタとメールアドレスを結びつけ、担当クラスと当日の予定から支部・スタジオを推定する。同日に担当候補が複数ある場合だけ、クラスを1回選択してもらう。

## 3. 既存システム

### Apps Scriptマニフェスト

- タイムゾーン: Asia/Tokyo
- V8ランタイム
- YouTube Data API v3 / Drive API v2
- Drive、Sheets、YouTube、外部HTTP通信のOAuthスコープ
- 外部ライブラリ `VideoUploaderLib`
- `developmentMode: true`

外部ライブラリのソースは自社管理ではない。

### 表側のApps Script

確認できている外部ライブラリ呼び出し:

```javascript
VideoUploaderLib.processFormSubmit(e);
VideoUploaderLib.processAllExistingRows();
VideoUploaderLib.uploadVideoByBranch(branchName, YouTube);
```

表側には以下も存在する。

- フォーム送信トリガー / 管理メニュー / 支部別YouTube投稿関数 / 手動アップロード / 時間主導型の未処理確認 / 完了行の非表示 / YouTube API診断

現行コードのコメントでは、支部ごとのGoogleアカウントで支部別トリガーを設定する方式になっている。

### 回答シート

- 37列、確認データ 2,582件（2026-01-20〜2026-07-22）
- YouTube投稿成功 2,569件 / 投稿取りやめ 11件 / 投稿失敗 2件

失敗2件は、動画ではなく `image/jpeg` がアップロードされたことが原因。

入力列: タイムスタンプ、メールアドレス、動画、支部、支部別スタジオ、レッスン日、講師名、アーティスト名、曲名、ジャンル、希望ハッシュタグ、希望タイトル

自動・管理列: 支部、スタジオ、動画URL、タイトル案、最終タイトル、ハッシュタグ、概要欄、投稿チャンネル、投稿OK、投稿日時、投稿ログ、投稿取りやめ、動画提出日、動画撮影日

現行システムは固定列番号へ依存しており、「列の挿入は禁止」とされている。

詳細な列定義と生成仕様は `現行システム_仕様復元書.md` を参照。

## 4. 現行データから判明した問題

- 希望タイトルが136件入力されているが、最終タイトルへ一度も採用されていない。
- ジャンル名が「ダンス」で終わる場合、「女性アイドルダンスダンス」などの二重表現が発生している。
- 初期10件に `{{地名}}` の置換漏れがある。
- `KPOP`、`K-POP`、`kpop` などの表記揺れがある。
- スペース、全角スペース、記号を講師側に除去させる設計になっている。
- ファイルのMIMEタイプを投稿前に検証していない。
- 「愛知」から「名古屋」への名称変更がデータ内に存在する。
- 東京の「萩窪」が正式名称か「荻窪」の誤記か要確認。
- 投稿成功は投稿ログ文字列で判定しており、媒体別の状態管理がない。

## 6. 媒体別の方針

### YouTube

- 8支部それぞれにチャンネルがある。
- 元動画を原則として再加工・再圧縮せず投稿する。
- タイトル、概要欄、ハッシュタグは自動生成する。
- 元動画はDriveへ保存する。

### Instagram

- 支部別のアカウントへ投稿する前提。
- SNS用加工版を作る。
- 投稿前に本部がLINEで確認する。

### TikTok

- 現状は1アカウント程度。特定支部用か全支部共通か未確定。
- Business Accountではない可能性があるが、フォロワー数自体は動画準備の障害ではない。
- 自社用の内部投稿ツールはTikTok Direct Post API審査の想定用途に合わない可能性が高い。
- 初期は次のいずれかを使用する。
  1. 加工動画と投稿文を担当者へ渡し、TikTokアプリから手動投稿
  2. Upload APIでTikTok受信箱へ送り、アプリで最終投稿
- 講師にはTikTok投稿作業をさせない。

## 7. SNS用動画の初期加工

最初は失敗しにくい加工に限定する。

- 9:16 / 1080×1920
- 30秒以内の確認
- 回転情報の補正
- 横動画や余白がある場合の縦動画化
- 必要に応じて背景ぼかし
- 支部名、講師名、クラス名の表示
- 会話がある場合だけ字幕
- InstagramやTikTok由来のウォーターマークを付けない

元動画がすでに縦・30秒以内なら、振付を勝手に途中で切らない。AIのハイライト抽出、自動カット、人物追尾は後続フェーズとする。

## 8. 本部LINE承認

LINE通知に表示する内容:

- 支部 / スタジオ / 講師 / クラス / 曲名 / 加工版プレビュー / 投稿文 / 投稿予定媒体

操作:

- 全媒体へ投稿 / 投稿先を選択 / 投稿文を修正 / 差し戻し

講師は承認操作を行わない。

## 9. 推奨アーキテクチャ

```text
GitHub Pages 講師ポータル
  ↓
動画アップロード画面
  ↓ 署名付きURLを要求
Cloudflare Worker（動画受付専用）
  ↓
ブラウザからR2へ直接アップロード
  ↓
投稿ジョブ登録
  ↓
動画検査・SNS用加工
  ↓
本部LINE承認
  ↓
媒体別Publisher
  ├─ YouTube
  ├─ Instagram
  └─ TikTok
```

動画本体をApps ScriptやWorkerへプロキシしない。Workerは短時間有効なR2アップロードURLを発行し、講師端末からR2へ直接送る。

### 既存Cloudflare資産

別案件で以下が実装・実地テスト済み。

```text
LINE
→ Cloudflare Workerで署名検証
→ Cloudflare Queue
→ 即200
→ Queue Consumer
→ GAS
→ Google Sheets台帳
```

既存Worker: `worker/lr-line-relay`

動画投稿用は責務を分離する: `worker/lr-video-upload`

Cloudflareアカウント、Queueの設計思想、Wranglerによるデプロイ方法は流用できるが、既存LINE受信Workerへ動画機能を混在させない。

## 10. データ設計

既存フォーム回答シートは過去記録として保存し、新システムでは固定37列へ依存しない。

### 講師マスタ

講師ID / 講師名 / Googleメールアドレス / LINE userIdまたはgroupId / 稼働状態 / 担当クラス候補

### 支部マスタ

支部ID / 表示名 / YouTubeチャンネル / Instagramアカウント / TikTok対象 / Drive保存先 / 投稿テンプレート / 有効・無効

### スタジオマスタ

スタジオID / 支部ID / 表示名 / 有効・無効

### 投稿ジョブ

ジョブID / 元動画ID / 講師ID / 支部ID / クラスID / 元動画状態 / 加工状態 / LINE承認状態 / YouTube状態 / Instagram状態 / TikTok状態 / 各投稿URL / エラー / 再試行回数 / 作成日時 / 更新日時

推奨状態:

```text
RECEIVED
VALIDATING
VALIDATION_FAILED
PROCESSING
WAITING_APPROVAL
APPROVED
PUBLISHING
PARTIALLY_PUBLISHED
PUBLISHED
REJECTED
FAILED
```

媒体ごとに状態を分け、Instagramだけ失敗した場合はInstagramだけ再実行する。承認ボタンの多重押下でも二重投稿しない冪等性を持たせる。

## 11. 制約：決定的コードとLLMの責務分離

システム内でLLMを使うかどうかは実装側の判断に委ねるが、使う場合は次を**必須の制約**とする。

以下は必ず決定的なコードで処理する。LLMの判断結果に依存させない。

- 本人認証 / 支部・投稿先の決定 / ファイル保存 / MIMEタイプ、サイズ、尺の検査 / LINE承認状態 / API認証 / SNS投稿 / 冪等性 / リトライ / ログ

**LLMへアクセストークンや投稿権限を直接渡さない。** LLMに自由判断で投稿させない。

LLMを使う場合の適用範囲の提案は `ai-orchestration-spec.md` を参照（採否は実装側の判断）。

## 12. 段階的な開発フェーズ

| Phase | 内容 |
|---|---|
| 0 | 棚卸し（現行トリガー、Script Propertiesのキー名、Drive保存先、支部別アカウント、講師マスタ、課題曲データ、既存リポジトリとデプロイ構成） |
| 1 | 講師ポータルのアップロード（`lr-portal` に画面追加、講師認証、R2直接アップロード、ジョブ登録、完了画面） |

| 3 | SNS加工（動画検査、9:16正規化、SNS用マスター作成、プレビュー） |
| 4 | LINE承認（承認通知、修正、差し戻し、冪等性） |
| 5 | Instagram（支部別OAuth、加工動画の投稿、結果取得、エラー再実行） |

| 7 | 切り替え（新旧並行稼働、受入テスト、ロールバック確認、外部 `VideoUploaderLib` の停止・削除） |

## 15. 初期の受入条件

Phase 1〜6は、最低限以下を満たして完成とする。

- 講師がスマホで動画を選び、提出できる。
- 通常時の講師入力は動画選択だけ。
- 元動画が欠損せず保存される。
- 支部・講師・クラスが正しく判定される。
- 動画以外のファイルを投稿前に拒否できる。
- 本部LINEでプレビューと投稿先を確認できる。
- 承認前にSNSへ公開されない。
- YouTubeへ元動画が投稿される。
- Instagramへ加工版が正しい支部アカウントで投稿される。
- TikTok用の加工版と投稿文が準備される。
- 同じジョブを二重投稿しない。
- 一部媒体の失敗時に、その媒体だけ再実行できる。
- エラー内容と投稿URLが記録される。
- 現行システムへ戻せる。
