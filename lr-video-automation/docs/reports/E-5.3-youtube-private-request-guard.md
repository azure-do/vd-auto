# E-5.3 YouTube private無条件固定ガード 実装報告

- Status: implemented locally（Issue #20）
- 外部接続: なし
- 対象: YouTube clientを呼ぶ直前のrequest builder、fake/mockテスト、安全な監査記録

## 1. 実装した安全境界

E-5 serviceは`buildPrivateYouTubeUploadRequest`でrequestを作り、
`dispatchGuardedPrivateYouTubeUpload`からYouTube clientを呼ぶ。request builderは呼び出し元の
objectをそのまま渡さず、YouTube `videos.insert` 用のvisibility部分を次の定数だけから作り直す。

```text
part=status
requestBody.status.privacyStatus=private
```

作成後のrequestと内部objectは凍結し、client呼び出しまでの書き換えも防ぐ。
provider request、request body、statusを含む送信objectはすべてnull-prototypeで作り、
`Object.prototype.publishAt`や`Object.prototype.toJSON`が汚染されても、予約公開fieldの混入や
直列化時のpublic本文への差し替えが起きないようにした。
入力判定、再構築、凍結、provenance確認に使うbuilt-in関数はmodule初期化時に参照を固定した。
module読込後に`hasOwnProperty`やObject/Reflectの静的関数を書き換えられても、動的に
汚染済み関数を再取得して判定を迂回しない。すでにrealmが破壊された状態でmoduleを読み込む
ケースは保証対象外とする。
service入力も実行開始時に、plainなown data propertyだけを持つobjectか、
許可keyが完全一致するか、sourceの形も正しいかを検証し、1回だけ不変snapshotを作る。
以後のclaim、R2検証、client送信、結果記録、監査はすべてこのsnapshotを使い、
呼び出し元が後からjob、target、承認版、actor、sourceを書き換えても影響されない。
job ID・投稿先・承認版・sourceの値検証は共通関数に集約し、serviceとbuilder直接呼び出しの
両方へ適用する。空ID、不正な版、非正整数サイズ、不正チェックサム、URL等のobject keyは
client呼び出し前にTypeErrorで停止する。builderは冪等キーもjob・YouTube・投稿先・承認版の
JSON配列文字列と完全一致することを確認し、別ジョブ・別投稿先等のキーを使わせない。
キー比較では文字列を個別にJSON化し、既存のtoJSON汚染テストを維持する。
通常入力と拒否監査用の必要情報抽出は同じsnapshot関数を使い、許可fieldの検査だけを
各入口に残す。fake専用定数・処理はcore dispatchより後の区画へまとめた。
raw adapter登録を公開しないため、fakeは引き続き同じmodule内に置く。
request builderはYouTube client呼び出しの例外処理より前に完了させるため、
builderによるポリシー拒否を通信の結果不明として扱わない。

builderが作成したrequestだけを許可する型brandと実行時provenanceを付け、
`dispatchGuardedPrivateYouTubeUpload`がclient呼び出しの直前にprovenance、null-prototype、
`privacyStatus=private`、`publishAt`不存在を再検証する。adapterの実行関数はmodule内部の
WeakMapだけに保持し、serviceや一般callerにはmethodを持たない不透明なclient handleだけを渡す。
そのためdestructureや`Reflect`でもraw upload capabilityを取り出せない。
公開するtest fake factoryも、固定の観測結果・失敗・一時停止というデータだけを受け取り、
任意callbackやprovider wire bodyは受け取らない。
fake controllerのoptionsも作成時にplain own-data、許可key完全一致、列挙可能propertyを検査し、
許可するのはbooleanの`pauseBeforeResult`だけとする。未知key、symbol、非列挙、継承、accessor、
custom prototypeは値を読まずに拒否する。
production sourceは再帰ASTテストで走査し、旧raw method、境界外のadapter capability、
guard済みdispatch箇所の意図しない増加を検出する。import alias、定数文字列を組み立てた
computed method、サブディレクトリ内のprivate factory参照も反例fixtureで検出する。

E-5.1の入口検証も維持する。入口で拒否した場合はジョブを
`APPROVED`のままにし、YouTube/R2 clientを呼ばない。監査記録には
`publication.policy_rejected`と固定error codeだけを保存し、拒否された生値は保存しない。
監査detailsもnull-prototype objectから直列化し、prototype汚染による改変を防ぐ。
監査INSERTはDB内で、ジョブが`APPROVED`、承認済み版とYouTube投稿先が一致、
投稿台帳が`PENDING`、かつ読み取った`row_version`が現在も一致する場合だけ成立する。
通常投稿が先に進んだ場合や承認外targetにstale監査を残さない。
この条件付きINSERTが成立しない場合は、拒否処理の成功応答を返さず
`CONCURRENT_UPDATE`でfail closedとする。

## 2. 拒否条件

- `privacyStatus` は省略・undefinedならprivate固定、それ以外は完全一致の `private` だけを許可
- `public`、`unlisted`、大小文字違い、前後空白、空文字
- null、boolean、number、object、arrayなどの不正型
- `publishAt` propertyの存在（値がnullやundefinedでも拒否）
- 設定値としてのpublic指定。監査済みや公開許可フラグは判定に使用しない
- `providerRequest.requestBody.status`、設定object、source内、未知field等へのポリシー値注入
- 非列挙property、継承property、accessor、symbol、custom prototypeを使った迂回
- `Object.prototype`から継承した`publishAt`、visibility、provider request等の既知政策field
- builderを通っていない、形だけprivateに似せたrequest
- job・投稿先・承認版・sourceの契約違反、および実行対象と一致しない冪等キー

入力shape自体が不正でも、正しいjob、target、承認版、actor、sourceを安全にown data propertyから
抽出できる場合だけ上記の条件付き監査を残す。継承objectやaccessorなど、安全な識別子を確定できない
場合は監査を無理に作らず例外で停止する。どちらもR2/YouTube clientは呼ばない。

省略時は呼び出し元の既定値に任せず、builderが必ず`private`を設定する。
未知fieldやネストした送信本文は黙って捨てず、構築前に拒否する。

builder完了後のR2検証とYouTube client送信は、元の可変inputではなく、
同じ凍結済み`uploadRequest.source`を使う。処理中のawait間に元inputが変更されても、
R2で検証したobjectとclientへ渡すobjectは一致する。

## 4. 後続実装への制約

E-5.6で実resumable adapterを追加する場合は、この安全境界module内部にadapter生成を実装する。
adapter実行関数や任意callbackを受け取るfactoryは公開せず、不透明handleだけをserviceへ渡し、
本builderが返す`providerRequest`をそのまま使う。公開対応、予約公開、ガード無効化設定は
E-5.3の拡張として追加せず、必要な3条件が揃った後の別実装単位で扱う。
E-5.6追加時には、実adapterがこの条件を守ることを改めて実装・テスト・独立レビューで確認する。
今回の検証は既存fake境界についての結果であり、未実装の外部adapterの動作は保証しない。
