# E-4.1 承認依頼・承認操作・承認済みコンテンツ版の模擬実装

- 状態: ローカル実装済み（Issue #16）
- 外部接続: なし
- 使用データ: 架空の内部ID・ダミー文面・ダミーオブジェクト参照のみ

## 要点

- 登録済みの承認者だけが、検証済みの動画を承認または却下できる。
- 同じ操作の再送や同時操作があっても、最初に確定した操作だけを有効にする。
- 承認後は動画内容や投稿先をすり替えられず、変更時は再承認を必要とする。
- 今回は模擬環境での検証であり、実際のLINE・動画・SNS投稿には接続していない。

## 1. 実装した契約

- 入口検証済み・クラス確定済み・アップロード完了済みで、状態が`WAITING_APPROVAL`のジョブだけを承認対象にする。
- 承認依頼時に、ジョブ、動画オブジェクト参照、チェックサム、加工結果、文面、投稿対象、期限から改ざん検知用の要約値（フィンガープリント）を作り、D1に固定する。
- 固定スナップショット列はD1トリガーで更新を禁止する。さらに承認・再開・確定済み再送の各入口で保存JSONとフィンガープリント・承認版を再計算し、不一致や不正JSONを`SNAPSHOT_TAMPERED`で監査・拒否する。承認操作の確定記録にも検証済み固定値を条件として含め、検証直後の差し替えを防ぐ。
- 操作トークンは暗号学的乱数から作る。承認依頼にはハッシュだけを保存し、生のトークンはローカル模擬通知の送信待ち箱にのみ保持する。承認依頼の作成結果には返さず、トークンは監査ログとレポートに記録しない。
- 模擬承認者の許可リストにある有効な内部IDだけが操作できる。不明・無効化済み・形式不正IDは拒否し、生値ではなくフィンガープリントと固定理由コードを監査する。
- 操作前に`DECIDING`の最初に確定した操作内容（操作、操作応答ID、承認者ID、時刻、版）を条件付きで固定する。同じ更新条件で許可リストの有効性を再確認し、確認直後の失効競合を防ぐ。承認と却下が同時に行われても、最初に確定した操作だけを引き継いで処理する。
- D1の状態遷移ガードで`PENDING → DECIDING/EXPIRED → 操作に対応する最終状態`だけを許可し、最初に確定した実行者・操作・操作応答・版の直接差し替えや、承認待ちから最終状態への迂回を拒否する。
- 正規の承認操作の確定記録は、承認依頼・操作応答（`postback`）・実行者・操作・承認版・時刻・固定フィンガープリント・トークンハッシュを結ぶ`intent_proof`とともに、承認依頼の`DECIDING`化・通知取消と同じD1一括処理で1件だけ作る。状態遷移ガードは、最初の操作を1件だけ確定する`approval_decision_claims`の完全一致を必須とし、再開・最終化・確定済み再送でも証明値を再計算する。
- `approved_content_version`は固定済みオブジェクト参照、チェックサム、コンテンツフィンガープリント、投稿対象フィンガープリントから決定的に作る。
- 承認時に、同じ操作が再送されても結果を1件に保つ既存E-1の冪等台帳を「ジョブ + 媒体 + 投稿先 + 承認版」で作り、模擬投稿処理の送信待ち箱へ集約イベントを1件作る。却下ではどちらも作らない。
- 汎用`job.transition.requested` Queueから`APPROVED`/`REJECTED`への遷移を拒否する。呼出元が指定した版・投稿先で許可リストやトークンの確認境界を迂回できない。

## 2. ローカル模擬検証

```bash
cd worker
npm run check
npm run demo:e4
npm run verify:e4:migration-upgrade
npx wrangler deploy --dry-run
```

E-4.1専用テストで、次を確認する。

- 正常な承認・却下
- 許可リストの一致・不一致・無効化済み・形式不正
- 同一承認依頼の再送、同一操作応答（`postback`）の再送、多重押下、同時承認
- 承認と却下の競合、最初の操作確定直後の停止・再開
- ジョブ、コンテンツフィンガープリント、投稿対象の改変
- D1トリガーによる固定スナップショット列の直接更新拒否、トリガーを外した反証環境での保存JSON改変拒否、検証直後の差し替え競合拒否
- 未知トークン、別ジョブへのトークン使い回し、期限切れ、期限切れ後の新規トークン再発行
- 通知配送時に期限切れ承認依頼を`EXPIRED`、未送信通知を`CANCELLED`へ収束させ、期限切れトークンを配送しないこと
- 承認確定前後の停止・再配信
- 模擬承認通知と模擬投稿処理の受信側が、安定した通知・イベントIDを永続的な冪等キーとし、受理直後の応答喪失、処理権利期限の回収、再送があっても実際の模擬副作用を1件に保つこと
- 同じ通知・イベントIDが別のデータフィンガープリントに使い回された場合は衝突として安全側に拒否し、送信待ち箱を配送済みにしないこと
- 受信接続部自身が実データからフィンガープリントを再計算すること。通知トークンは生値ではなくSHA-256ハッシュをフィンガープリント要素にし、通知・投稿イベントの改変は配送記録の作成前に安全側に拒否すること
- 通知・投稿処理の送信待ち箱にある固定データ列をD1トリガーで更新禁止にし、配送直前に承認依頼と再照合すること。承認操作の確定記録にも検証済み固定値を条件として含め、検証直後のトークン・投稿対象・フィンガープリント差し替えを`OUTBOX_TAMPERED`で拒否すること
- `PENDING`から最終状態への直接変更と、`DECIDING`に固定された最初の承認者・操作・版の直接変更をD1で拒否すること
- 承認操作の確定記録なしの`PENDING → DECIDING`直接変更を拒否し、不正な証明値を持つ偽の確定記録と偽`DECIDING`があってもジョブ遷移・投稿処理を作成しないこと
- 最初の操作確定後に承認者が失効しても、保存済みの確定操作だけを回復し、確定済みの同一操作応答（`postback`）は失効後も既存結果を返すこと
- 許可リスト照合直後に承認者が失効した未確定の操作は拒否し、ジョブ・投稿処理を変更しないこと
- 承認後の文面または投稿対象変更を`REAPPROVAL_REQUIRED`で拒否し、既存承認版にすり替えないこと
- `VALIDATION_FAILED`、`CLASS_UNRESOLVED`、処理中、却下済み、未完了アップロード、未解決クラスが承認不可であること
- 承認監査・承認記録・投稿イベントが各1件であること
- データベース移行の新規適用・既存DB更新・再適用・失敗時の巻き戻し

## 3. 後続の実LINE接続へ渡す境界

| 境界 | E-4.1で固定済み | 後続で必要 |
|---|---|---|
| 通知 | 送信待ち箱ID、固定データ、処理権利期限、受信側の安定ID冪等 | `lr-line-relay`単一Webhook入口の実証結果に従う接続部。受信側も通知IDを永続冪等キーとする |
| 承認者 | 有効・無効を持つ許可リスト契約 | 実LINE利用者IDの安全な登録・失効運用（値は秘密保管） |
| トークン | 短期、対象結び付き、ハッシュ照合 | 本番用秘密・乱数生成・配送・失効・ログマスク |
| 操作応答 | 承認操作の確定記録と最初に確定した操作内容からの再開 | LINE署名検証と操作応答（`postback`）の正規化接続部 |
| 投稿処理 | 承認版と投稿対象を固定した送信待ち箱と、受信側イベントIDの冪等性 | 媒体別Queue・投稿処理への実配送。受信側も投稿イベントIDを永続冪等キーとする |

## 4. 安全境界と残存事項

- LINE Messaging API、実Webhook、実利用者ID、実グループ、実メッセージ、実動画、Cloudflare実リソース、YouTube・Instagram・TikTokに接続しない。
- `public`、`unlisted`、`publishAt`と未知フィールドは契約入口で拒否する。
- 承認後の入力変更は固定済み版を書き換えず`REAPPROVAL_REQUIRED`で停止する。合意済みの共通契約v1に`APPROVED`から承認待ちへ戻す状態遷移は存在しないため、同一ジョブを戻す操作は独断で追加していない。実運用で「承認取消して再加工」を必要とする場合は、状態契約を先に承認して別Issueで追加する。
- 本実装は模擬実装のため、実LINE署名検証・実利用者ID・実通知・実投稿処理は未確認である。
- D1管理者権限でトリガーを削除し、実装と同じ証明値を計算して複数テーブルを意図的に偽造する脅威は本Issueのローカル模擬範囲外である。本番ではD1・配備権限を最小化し、通常のWorker経路以外から書き込ませない。
