# Runbook: 外部委託者との継続開発

- Status: accepted（2026-08-15）
- 入口: [外部委託者 オンボーディング](external-contributor-onboarding.md)
- 出口: [退職時 認証情報 失効](offboarding-credential-revocation.md)

## 1. 目的

設計図と受入条件を渡し、細かなエンジニアリング判断は委託者へ任せる。亮さんの都度承認待ちで実装を止めない。
通常作業はGitHub Issueの目的・成果物・受入条件だけで開始し、外部接続・課金・本番などの副作用がある場合だけ追加の作業パッケージ条件を定義する。

## 2. 役割

| 役割 | 担当 | 日常の責務 |
|---|---|---|
| オーナー / 最終決定 | 亮さん | 業務判断、課金、本番・公開、権限範囲拡大の承認 |
| PMO / 一次レビュー | Codex | Issue整備、進行、技術レビュー、承認事項の集約 |
| SE | 外部委託者（GitHub: `sheet-maker`） | 技術選定、作業分割、実装、テスト、PR提出 |
| 監査 | PMO・SEとは別のAI | フェーズ境界、重要設計、静かに壊れる変更の独立監査 |

オーナーを日常のコマンド実行者や全コードの一次確認者にしない。PMOが実行可能な操作と技術確認を引き取り、オーナーには人間にしか決められない事項だけを示す。

## 3. Issueに必要な情報

通常の実装Issueに必要なのは次の3点だけとする。

- 目的
- 成果物
- 受入条件

既存のRepository内で、ローカル・fake・mock・ダミーデータを使う調査・実装・テスト・PR提出は、追加承認なしで進める。

次を含むIssueだけ、対象環境・許可する副作用・課金上限・停止方法を追加し、**作業パッケージ**としてまとめて承認する。

- 外部API、クラウド、実アカウントへの接続
- 課金resourceの作成または予算増額
- 本番・実データ・実SNSを使う操作
- 権限や秘密情報の対象拡大

オーナーが作業パッケージを承認した後は、その記載範囲内の調査・実装・テスト・外部接続について都度承認を求めない。範囲を超える必要が生じた場合だけIssueを更新し、差分を承認する。

## 4. SEへ委任する技術判断

次は受入条件を満たす限り、SEが是々非々で決める。

- DB製品、ライブラリ、framework、内部API、module構成
- table・column・index・migrationの詳細
- test framework、fixture、mock、CIの構成
- Issue・PRの分割、実装順、branch運用
- エラー処理、監視、性能改善の具体方式
- 既存設計と矛盾しない範囲の技術的な代替案

判断理由はPR本文へ簡潔に記録する。状態正本、認証、公開条件などの設計境界を変える場合だけADRとオーナー判断へ上げる。

## 5. 止めずに進める操作

- 公開一次資料の調査、方式比較、RFC・設計案の作成
- 作業ブランチへのcommit / push、PR作成、レビュー対応
- リポジトリ内のコード・文書・テストの変更
- ローカル、fake、mock、ダミーデータを使う検証
- パッケージで指定済みの会社所有・開発専用環境での操作
- 指定済みの予算・クォータ内での実行
- 失敗時に開発用runnerを止める、機能フラグを無効化するなどの可逆な安全措置

## 6. オーナーへ戻す停止点

次の場合だけ停止し、PMOが選択肢・推奨案・影響を1件にまとめて亮さんへ出す。

- 業務要件、製品ゴール、受入条件または設計境界の変更
- 新しい有料契約、課金開始、承認済み上限の超過
- 本番環境、現行GAS、実支部SNS、実動画、個人情報への接続
- YouTubeの `public` / `unlisted` / `publishAt`、SNSへの実投稿、外部への送信
- アカウント・チャンネル・プロジェクト・重要データの削除
- 権限、秘密情報、対象アカウントの範囲拡大
- Git履歴の書き換え、`main`への直接push、branch protectionの変更

判断待ちの間も、SEは同じパッケージ内の未依存作業または予備タスクを進める。

## 7. 作業を止めないキュー

PMOは常に次の3枠を用意する。

1. **実行中**: 現在の主作業
2. **次**: 主作業の受入後すぐ着手できる作業
3. **予備**: 外部接続や業務判断を要しない調査・テスト・文書整備

SEが判断待ちになった場合は予備へ移り、回答後に主作業へ戻る。新しい業務要件を予備作業として勝手に確定しない。

## 8. レビューと決定

1. SEがPRを提出する。
2. PMOが仕様、テスト、秘密情報、差分範囲を一次レビューする。
3. 技術的に閉じる指摘はPMOとSEで解消する。
4. 委任範囲内の技術選定は、PMOレビュー後にオーナー判断を待たずに確定する。
5. オーナー判断が必要な場合だけ、PMOが「推奨案・代替案・影響」を短くまとめる。
6. 状態正本、認証、課金、個人情報、フェーズ境界の変更は別AI監査へ回す。
7. 条件を満たしたPRをbranch protectionに従ってmergeする。

確認事項は随時小分けにせず、原則としてまとめて提示する。緊急停止が必要な安全問題だけは即時連絡する。

## 9. 先行準備

PMOは次フェーズの依存物を、現在フェーズの作業中に準備・確認する。

| 依存物 | 必要になる前 | 方針 |
|---|---|---|
| Cloudflare / R2 開発アクセス | E-3着手前 | 会社所有の開発専用環境、予算上限、ダミーデータ、対象resourceを作業パッケージに明記 |
| クラスマスタ参照 | E-2着手前 | 禁止情報が無ければ元シートをViewer共有。含まれる場合は必要列だけの自動同期・読み取り専用ビューを共有。手更新のダミーは作らず、テストfixtureだけダミーにする |
| テストYouTubeチャンネル | E-5.2着手前 | 既存の `LRVideoE0ATEST`（`@videotest_lr`）を再利用し、新規作成しない。会社所有アカウントがOAuth同意し、tokenは秘密保管、private固定、channel ID照合。Studio招待はAPI権限の代替にしない |
| 外部API接続 | E-0b / E-0c等の着手前 | 接続先、テストアカウント、副作用、停止方法をまとめて一括承認 |

## 10. 先方が読む順序

毎回Repository全体を読み直させない。通常は次だけを渡す。

1. 対象のGitHub Issue
2. `README.md`
3. `docs/design/architecture-overview.md`
4. `docs/design/implementation-units.md` の対象部分
5. `docs/contracts/`
6. Issueに明記された関連ADR

`docs/baseline/`、`docs/handover/`、対象外RFCは必要になったときだけ参照する。派生文書と正本が食い違う場合は、accepted ADR・design・contractsを優先する。
