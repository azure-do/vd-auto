# Runbook: 外部委託者 オンボーディング（アクセス付与）チェックリスト

- 準拠: [ADR-0014](../decisions/0014-assets-under-company-owned-accounts.md)（成果物と作業環境は最初から自社所有アカウント配下に置く）
- 対になる手順: [退職時 認証情報 失効チェックリスト](offboarding-credential-revocation.md)（ADR-0012）。本書が入口、あちらが出口。
- 着手後の進行: [外部委託者との継続開発](external-contributor-delivery.md)（作業パッケージ単位で一括承認し、都度承認待ちを作らない）
- **重要**: 秘密値（パスワード／トークン／シークレット／実メールアドレス）を本書・コミット・ログ・チャットに書かない。記録するのは **サービス名・フォルダID・公開ハンドル・所有権・実施者・日時** のみ。

## 主軸

本書の目的は情報漏洩の防止ではなく、**成果物の所有権を最初から自社に置くこと**である。権限を絞ることはその副産物にすぎない。判断に迷ったら「この資産の所有者は誰になるか」で決める。

- 個人アカウントのマイドライブに成果物を作らせない
- 「後で移管する」を手順に含めない。移管が発生した時点で失敗
- アクセス付与の単位はフォルダ。フォルダ名はリポジトリ名に対応させる

例外は §5。認証情報の統合を委託範囲に含める場合、委託者は実際の秘密値を参照するため、入口で絞る方式が成立しない。出口（失効・再発行）で担保する。

## 0. 付与前に確定させること（未了なら招待しない）

- [ ] 業務委託契約／NDA の締結（秘密保持・成果物の著作権譲渡・再委託の可否・終了時の返還消去）
- [ ] 委託範囲の明文化（`docs/design/implementation-units.md` の単位で指定）
- [ ] 契約期間・アクセス有効期限（終了日を先に決める。無期限にしない）
- [ ] 窓口と承認者を明記。**業務判断・本番反映は委託者に渡さない**
- [ ] 生徒・講師の個人情報、実動画を渡さない方針の確認

- [ ] その中に作業用サブフォルダを作成
- [ ] 既に個人のマイドライブに作った資産があれば、**招待前に**共有ドライブへ移動
- [ ] 移動後、所有者が個人から共有ドライブへ変わったことを確認
- [ ] 稼働中の GAS を移す場合は、トリガー・実行アカウントの動作確認をセットで行う（新規着手分と分けて実施）

## 2. 委託者用アカウント

- [ ] **この用途専用で中身が空のアカウント**を用意する
- [ ] 既存アカウントを流用する場合は、渡す前に Drive・Gmail の中身を確認し、空にする
  - 管理コンソールのストレージ使用量で確認（Drive・Gmail・フォトの合計値なので内訳を見る）
  - ゴミ箱に入れただけでは容量が残る。ゴミ箱まで空にする
  - **所有者は自分のファイルを常に参照できる。共有解除では対処できない**
- [ ] 組織部門（OU）に `外部委託者` を作成し、そのアカウントを配置
- [ ] 当該 OU に対して 2段階認証を強制、Drive の外部共有を制限、不要アプリをオフ
- [ ] 復旧用メール・復旧コードを**会社管理**に設定（本人管理にしない）
- [ ] パスワードは本人に直接渡し、初回ログイン時に変更させる（文書・チャットに書かない）

> 既存アカウント流用の失敗例（2026-08-14）: 業務自動化の実行主体として使われていたアカウントが、給与明細37名分と給与計算シートを**所有**していた。別の候補アカウントには過去の面接録画が残っていた。中身の分かっている専用アカウントを用意するほうが速く、洗い漏れが原理的に発生しない。

## 3. Drive のアクセス付与

- [ ] **共有ドライブのメンバーにはしない**（他プロジェクト・非開発フォルダまで見えてしまう）
- [ ] 該当プロジェクトの `開発_<リポジトリ名>` フォルダのみを個別共有（権限は編集者）
- [ ] 共有後、他のフォルダが見えないことを確認
- [ ] 付与日・権限レベル・有効期限を記録

## 4. GitHub

- [ ] **先に** `main` の branch protection を設定（直 push 禁止、PR 必須、レビュー承認1件以上）
- [ ] そのうえで Collaborator として招待。順番が逆だと、招待直後に直 push できる時間が生まれる
- [ ] 招待は**リポジトリ単位の Collaborator**（Organization Owner／Member には昇格させない）
- [ ] 権限は **Write** まで（Admin は付与しない）
- [ ] Actions の Secrets／Variables を付与しない。self-hosted runner を使わせない
- [ ] リポジトリに秘密値が無いことを再確認（fork とローカルクローンが発生する前提）
- [ ] `docs/baseline/` は変更禁止（原本）である旨を伝達
- [ ] 招待日・権限レベル・有効期限を記録（公開ハンドルのみ）

## 5. 認証情報の取り扱い（統合作業を委託する場合）

認証情報の統合（F-02 平文台帳の解消／F-03 管理方式の是正）を委託範囲に含める場合、委託者は実際の秘密値を参照する。除外リストによる防御が成立しないため、**出口（失効）で担保する**方式に切り替える。

### 5-1. 前提

- [ ] 委託者が参照した秘密値は、**すべて失効・再発行の対象**になるものとして扱う
- [ ] 契約終了時に、委託者が参照した全ての値を変更する（最終ローテーション）。これが唯一の確実な出口
- [ ] 作業単位が終わるごとに、その単位の値を変更する（中間ローテーション）。終了時に一括だと対象が膨らみ漏れる

### 5-2. ローテーション対象台帳

作業中、**委託者が参照した値を随時記録する**。これが無いと最終ローテーションで漏れる。

- [ ] 記録するのは **サービス名・キー名・保存場所・参照日** のみ（値は書かない）
- [ ] 記録先は招待制の管理シート。リポジトリには置かない
- [ ] 委託者自身にも記録させ、亮さん側の記録と突合する

### 5-3. 渡し方

- [ ] 平文台帳（`10_必要情報` / `URL,PW管理`）を**そのまま渡さない**。対象を列挙して個別に渡す
- [ ] 列挙外の値は渡さない。追加が必要になったら都度、台帳に追記してから渡す
- [ ] 値の受け渡しにチャット・メール・ドキュメントを使わない

### 5-4. 統合対象の線引き

アカウントのパスワードを渡すと、**そのアカウントが所有するデータも全て見える**。統合対象にどのアカウントを含めるかは、認証情報の話ではなくデータの話として判断する。

- [ ] 統合対象アカウントを列挙し、**対象外を明示**する
- [ ] 人事系（給与・採用）のデータを所有するアカウントは対象外とし、必要になった場合は亮さんが実施する
- [ ] 対象外アカウントの値を、台帳経由で誤って渡さないこと（§5-3 の「列挙外は渡さない」と同じ）

**lr-video-automation での線引き（2026-08-14）**

| 区分 | 内容 |
|---|---|
| 対象 | 支部マスタが持つ支部別アカウント3種（YouTubeチャンネル／Instagramアカウント／TikTokアカウント）と、支部別YouTube認証に使われている**支部ごとのGoogleアカウント**。支部は8つ（東京・千葉・埼玉・名古屋・大阪・京都・兵庫・福岡） |
| 対象外 | 業務自動化の実行主体アカウント（給与明細37名分・給与計算シートを所有）。人事系全般。hacomono／WordPress／予約／採用（動画に無関係。ADR-0012 で前倒し変更の対象） |

| 委託者に渡すアカウント | 開発用の専用アカウント（中身が空であることを確認済み。過去の面接録画は事前に整理済み） |

### 5-5. それでも渡さないもの

- [ ] 本番 GAS／VideoUploaderLib への変更権限（**検証完了まで停止・変更しない**の原則。認証情報の統合とは別）
- [ ] 生徒・講師・応募者の個人情報そのもの（認証情報ではない）
- [ ] 自社クラスマスタへの書き込み権限。参照は下記の読み取り専用方針に従う

### 5-6. クラスマスタは手動ダミー化せず、読み取り専用で渡す

委託者が必要とするのはマスタの参照と連携実装であり、編集権限ではない。手作業でダミーシートを作り続けると、実マスタとの差分と亮さん側の更新作業が増えるため、次の順で共有する。

1. 元シートの項目を確認し、Repository記載禁止情報（生徒・顧客情報、休講・欠勤理由、個人連絡先等）が含まれなければ、開発用アカウントへ **Viewer** で元シートを共有する
2. 禁止情報または委託範囲外の列が含まれる場合は、必要列だけを自動同期する会社所有の読み取り専用ビューを共有する。手更新のダミーシートは作らない
3. 委託者には再共有・権限変更・編集を許可しない。必要な変更はIssueで提案し、会社側がマスタの正本へ反映する
4. 自動テスト、ログ、スクリーンショット、Repositoryには実レコードを持ち込まず、ダミーfixtureを使う

読み取り専用共有は「実データをRepositoryへ複製してよい」という意味ではない。アクセスは専用アカウントと契約期間に限定し、終了時に解除する。

## 6. 開発環境の分離

- [ ] 開発用の Google Cloud プロジェクト／GAS プロジェクトを本番と別に用意
- [x] 既存の検証用YouTubeチャンネル `LRVideoE0ATEST`（`@videotest_lr`）を再利用する。新規チャンネルは作らず、本番チャンネルを使わせない
- [ ] 投稿は private 強制のまま検証（ADR-0013 / Q12）
- [ ] テストデータはダミー（実生徒・実講師・実動画を使わない）
- [ ] 委託者が扱うシークレットが必要になった場合は、**開発専用の別値**を発行（本番値を流用しない）

### 委託者に任せられない作業

弊社アカウントで作業させれば所有権は自動的に自社に帰属するため、大半は委託者が自分で用意できる。例外は次の3つ。

- [ ] **課金**: GCP の請求先アカウント紐付け、外部サービスの新規契約。課金権限は委託者に渡さない
- [ ] **既存YouTubeテストチャンネルの権限確認**: `LRVideoE0ATEST`のBrand Account接続状況とYouTube Studioの権限方式を確認する。会社所有は維持し、新規チャンネルを作らない
- [ ] **YouTube API用OAuth**: Studioの招待権限はYouTube APIに使えないため、会社所有アカウントが開発用OAuthクライアントへ一度だけ同意する。tokenは承認済み秘密保管へ置き、委託者へ所有アカウントのパスワードやtokenを渡さない。E-5.2で期待channel IDとの一致を必ず確認する
- [ ] **クラスマスタの参照設定**: 会社側が元シートの項目を確認し、元シートのViewer共有または必要列だけの自動同期・読み取り専用ビューを設定する。手更新のダミーは作らない

## 8. 作業ルールの合意（着手前に伝達）

- [ ] 秘密情報をコード・文書・コミット・ログ・チャットに書かない
- [ ] `docs/baseline/` を変更しない
- [ ] 本番（現行GAS／VideoUploaderLib）を停止・変更しない
- [ ] 成果物は PR で提出。`main` への直接反映はしない
- [ ] 新しい Drive 資産は指定された共有ドライブ配下に作る。個人のマイドライブに作らない
- [ ] 外部サービスへの接続範囲・副作用・課金上限を作業パッケージに明記する。承認済み範囲内は都度確認せず進め、範囲外だけ停止する
- [ ] 作業ブランチへのpushとPR提出は通常作業として許可する。`main`への直接pushとGit履歴の書き換えは禁止する
- [ ] 業務要件・製品境界・認証・状態正本・個人情報・課金は勝手に変えず `docs/open-questions.md` に起票する。ライブラリ、DB製品、内部構造、テスト、PR分割等の実装判断は先方が決め、PRまたは必要最小限のADRへ理由を記録する
- [ ] 生成AIに社内情報を投入する場合の可否とツールを合意
